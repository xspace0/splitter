## 一、数据模型层修改

### 修改 1：第二章引言 — 表数量与说明
- **修改时间**：2026-08-17
- **位置**：二、核心数据模型设计 开头

- **修改后**：系统核心包含 3 张业务主表 + 1 张权限关联表 + 1 张操作日志表，实现业务数据、权限体系与审计追溯的解耦。

- **修改时间**：2026-08-17

- **原文**：（无）
- **修改后**：补充 `status`（设备运行状态）与 `is_deleted`（台账记录删除）语义不同的说明，删除操作即 `is_deleted` 置 1。

### 修改 13：sys_user_community 表 — 新增 status 字段
- **修改时间**：2026-08-17
- **位置**：2.4 用户-社区关联表
- **原文**：（无此字段）
- **修改后**：新增 `status`（tinyint，权限状态：1-有效 0-已移除，默认 1）
- **原因**：权限移除需保留历史（权责可追溯），逻辑删除替代物理删除。

### 修改 14：sys_user_community 表 — 新增 update_time 字段
- **修改时间**：2026-08-17
- **位置**：2.4 用户-社区关联表
- **原文**：（无此字段）
- **修改后**：新增 `update_time`（datetime，最近变更时间，非空）
- **原因**：权限状态变更需要时间记录，原表只有 create_time 无法反映权限移除时间。

### 修改 15：sys_user_community 表 — 设计说明补充
- **修改时间**：2026-08-17
- **位置**：2.4 表后设计说明
- **原文**：仅说明「一个用户可被分配多个社区，一个社区可分配给多个用户；除超级管理员外，所有用户的可见社区范围均由该表的关联关系决定。」
- **修改后**：补充三点：
  1. 管理员/超级管理员的「全量社区可见」来自角色判定（硬编码），不依赖本表，避免逐一分配成本；
  2. 权限移除采用逻辑删除（status 置 0）保留历史，重新分配时复用记录恢复 status=1；
  3. 唯一索引 `uk_user_community (user_id, community_id)` 防止重复分配。
- **原因**：原文未说明管理员的社区权限来源、权限移除的语义、重复分配的防护，实现时易产生歧义。

### 修改 16：新增 2.5 操作日志表 sys_operation_log【整节新增】
- **修改时间**：2026-08-17
- **位置**：第二章末尾（新增整节）
- **原文**：（无此表）
- **修改后**：新增操作日志表，字段含 log_id、user_id、operation_type（LOGIN/CREATE/UPDATE/DELETE/ASSIGN/EXPORT 等）、target_type、target_id、operation_content（JSON 变更详情）、ip、user_agent、create_time；并说明为只追加表、批量操作合并记录。
- **原因**：4.1 模块明确提到「操作日志：记录所有关键操作，支持追溯」，但原数据模型完全缺失日志表，功能与模型矛盾。这是原版最严重的缺口。

## 二、角色与权限体系修改

### 修改 17：3.2 权限校验 — 身份校验补充
- **修改时间**：2026-08-17
- **位置**：3.2 规则 1
- **原文**：所有接口请求必须携带用户身份凭证，拦截未登录与禁用账号
- **修改后**：所有接口请求必须携带 JWT 身份凭证（access_token），拦截未登录、禁用账号（status=0）与已删除账号（is_deleted=1）
- **原因**：明确凭证类型与拦截条件，配合新增的 is_deleted 字段。

### 修改 18：3.2 权限校验 — 数据层过滤明确来源
- **修改时间**：2026-08-17
- **位置**：3.2 规则 2
- **原文**：操作员/查看者：仅查询 `sys_user_community` 中与自身关联的社区对应的数据
- **修改后**：操作员/查看者：仅查询 `sys_user_community` 中 `status=1` 且与自身关联的社区对应的数据；管理员/超级管理员通过角色判定不追加过滤（不依赖本表）
- **原因**：原文未说明管理员权限来源，实现时可能误将管理员也依赖 sys_user_community 导致无数据。

### 修改 19：3.2 权限校验 — 写操作补充水平越权防护
- **修改时间**：2026-08-17
- **位置**：3.2 规则 3
- **原文**：分光器增删改操作，必须校验该设备所属社区在用户的分配范围内
- **修改后**：补充：新增分光器时校验 `community_id` 必须属于用户可操作社区集合，防止通过篡改 community_id 实现水平越权
- **原因**：原文仅覆盖「修改/删除已有设备」的越权校验，遗漏「新增时通过 community_id 篡改越权」的场景。

### 修改 20：3.2 新增规则 4 — 社区停用后的数据可见性
- **修改时间**：2026-08-17
- **位置**：3.2（新增规则 4）
- **原文**：（无）
- **修改后**：社区 status=0 停用后，分光器数据仍保留可见（只读），不可在该社区下新增分光器；默认禁止编辑停用社区下的设备。
- **原因**：原文未定义社区停用后数据可见性，实现时不同开发者会做出不同处理，需统一规则。

## 六、新增章节

### 修改 29：新增「七、安全设计」整章
- **修改时间**：2026-08-17
- **位置**：第六章后（新增整章）
- **原文**：（无）
- **修改后**：新增 7.1 密码安全策略（bcrypt、复杂度、失败锁定、重置强制修改）、7.2 身份认证与 Token 机制（access+refresh 双 token、登出黑名单、状态校验）、7.3 越权防护（水平/垂直越权、敏感操作记录）、7.4 接口安全（登录态、参数校验、限流）。
- **原因**：原版仅在技术选型提到「JWT 身份认证」一句话，密码策略、token 刷新、越权防护等关键安全设计完全缺失，运维系统账号安全是底线。

### 修改 30：第八章技术选型 — 收敛与明确
- **修改时间**：2026-08-17
- **位置**：七、技术选型参考
- **原文**：Node.js（NestJS / Koa 框架）；如需移动端可配套 UniApp；JWT 身份认证 + 接口层数据权限全局拦截；也可对接微信云开发云函数实现轻量化部署
- **修改后**：
  - 后端明确选定 NestJS（去掉 Koa 二选一）；
  - 新增 ORM：TypeORM（原生支持软删除）；
  - 新增缓存：Redis（缓存权限范围、Token 黑名单、失败计数）；
  - JWT 明确为 access+refresh 双 token；
  - 部署方案明确主推云服务器+Node.js，云函数仅作轻量备选，二者互斥不混合。
- **原因**：原版 NestJS/Koa 二选一未定案；无 ORM 选型影响开发效率与 SQL 安全基线；无缓存方案权限校验性能差；云函数与常驻 Node.js 后端互斥，原表述易误解为可混合。
